# Exact frozen image publication

This mode moves an already frozen image through the existing Judger CI credentials into the existing registry repository. It does not build, change Config/User/Entrypoint/labels/layers, push latest, or activate services. Default build workflow behavior is unchanged. Workflow dispatch selects mode=exact-artifact, a git-tracked reviewed manifest under manifests/, and exact_publish=false for validation or true for the permitted tag publication.

All components publish only to registry.cn-beijing.aliyuncs.com/pre-sduoj/sduoj-judger with unique explicit component/date/source/config/architecture tags. New registry repositories are not assumed. Candidate-staging-only uses mandatory staging- prefix; qualified uses the normal component prefix. Existing tags are rejected; exact jobs serialize without cancellation. Registry-side immutability is still needed against external writers. No default tag is reused or overwritten.

Qualification gates bind productSource and the **actual archive config SHA256**, never Docker inspect.Id. Common gates: image-config-layer-verification, image-disclosure-review, image-smoke. Workload gates: Judger=native-formal/native-run/worker-runtime-junit; IDE=ide-api/ide-browser/ide-debug-lsp/ide-isolation/ide-capacity/ide-900s/ide-recovery; manager=manager-nonroot/manager-boot-assets/manager-feature. Combined-release is an additional required qualification receipt referencing the exact component identity; it is pending until the combined profile has actually passed.

States:

- candidate-only: validation permitted, publication rejected before authentication.
- candidate-staging-only: common image/config/layers, disclosure and smoke gates must pass; workloads and combined-release may truthfully remain pending. Publish only the unique staging tag for isolated production KVM staging. This breaks the registry-reference staging dependency without treating staging as serving traffic.
- qualified: common, component-specific and combined receipts must all pass. Publication still reports productionQualified=false. A separate production traffic gate must bind the final registry child digest and actual deployment acceptance; registry push never calls that gate passed.

Same-repository **draft-only** GitHub release assets provide authenticated transport with fixed asset IDs, size, ordered part hashes and whole archive hash. Draft assets are mutable; the reviewed manifest and checksums prevent replacement credit. Never publish the draft. Public repository status does not by itself make draft assets public; conversely, do not assume the existing registry is public. Before upload, privately review Config Env/User/Entrypoint/Cmd/labels/Volumes/history and image layers for embedded credentials or confidential content, recording limited scan scope and exact image identity in disclosure evidence. Docker Desktop build labels containing reviewed local source/output paths may be retained as noncredential local metadata; do not delete labels by rebuilding the image. No broad “no private information” conclusion follows from path/Env heuristics.

archive.py validates both legacy Docker-save and OCI-layout archives. It verifies OCI descriptors and detects conflicting compatibility manifest identities, hashes the compressed blob bytes separately, decodes raw/gzip/zstd streams to verify uncompressed diffIDs, and derives config and child manifest digests from archive bytes. zstd requires system libzstd and fails closed if unavailable. Docker29 inspect.Id may name the OCI manifest, not image Config. After load, use the returned load handle, re-save for config/platform/diffID comparison, and tag that verified handle. Registry read-back independently verifies actual child manifest config digest/platform/diffIDs. Config digest preserves the entire image configuration, including labels, without recreating it.

The archive/config/layer verifier may run without Docker by importing archive.inspect(path). The actual manager archive used during preparation was source423 snapshot, **not the latest manager source**: manifest87389097… and configd72bcd53… are different; four gzip blob digests and decoded diffIDs were verified. That format test is not current-image workload qualification.

Use JSON receipts from actual runs; pending is an explicit status, not a fabricated workload pass. Receipt downloads must remain in the same restricted draft release. Gate JSON must contain matching gate/status/productSource/configSha256, and its bytes must match the reviewed receipt SHA. The manifest schema and Python checks both enforce component-specific gate sets and tag constraints.

No credentials are downloaded from Actions, printed, stored as release metadata, or accepted through dispatch input. Existing DOCKER_USERNAME/PASSWORD are passed only to the pinned login action. Actions pins are verified from official GitHub refs. Actual asset transfer, Docker load/tag/push and remote registry parsing must be exercised on candidate-staging-only input before qualified production publication is used. Validation output is not a deployment receipt.
